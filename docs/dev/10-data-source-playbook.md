### 1.1 最重要的一条结论

**东财不是"挂了"，是"时好时坏"。**

同一个 `clist` 请求，19:47 返回 200 且数据正常，19:52 连续两次返回 `000`（连接失败）。
这说明它是**快速限流或边缘节点抖动**，不是服务下线。

**直接影响**：绝不能把东财任何接口当主源或兜底依赖——这正是 tdx-backtest 的 HANDOVER 里写下「东财 push2his 与腾讯分钟接口当前不可达，勿当兜底依赖」的原因。

### 1.2 第二条：板块 K 线两边都没有

- 东财 `push2his` 已不可用
- 新浪根本不提供板块 K 线

**所以板块 K 线必须自己算**（见 §4）。这反而是好事：本地库有 5560 只个股日线，聚合出来的序列比等上游更稳、可回溯。

## 2. 内化 tdx-backtest 的四个机制

它的 `datahealth.py` 设计得很对，直接内化（不复制代码，按我们的技术栈重写）。

### 2.1 声明式资产注册表

把「要什么数据」和「从哪取」分离，注册表是唯一事实源：

```js
// lib/sources/registry.js
const ASSETS = {
  'sector-list-industry': {
    cn: '行业板块列表', sources: ['sina-hy', 'em-clist'], risk: 'low',
  },
  'sector-list-concept': {
    cn: '概念板块列表', sources: ['sina-fljk', 'em-clist'], risk: 'low',
  },
  'sector-members': {
    cn: '板块成分股', sources: ['sina-node', 'em-clist'], risk: 'low',
  },
  'sector-kline': {
    cn: '板块K线', sources: ['local-aggregate'], risk: 'none',   // 不取上游
  },
  'market-snapshot': {
    cn: '全市场快照', sources: ['sina-quote', 'em-push2delay'], risk: 'low',
  },
  'zt-pool': {
    cn: '涨停池', sources: ['em-push2ex', 'snapshot-derive'], risk: 'med',
  },
  'stock-kline': {
    cn: '个股K线', sources: ['local-db', 'ths', 'sina'], risk: 'low',
  },
};
```

**`sources` 是有序兜底链**，第一个是主源。顺序不是随便排的，是实测出来的。

### 2.2 风险分级配速

| risk | 最小请求间隔 | 用在哪 |
|---|---|---|
| `none` | 0 | 本地计算（板块 K 线聚合、本地库读） |
| `low` | 0 | 新浪、腾讯（对频率宽容） |
| `med` | 0.3s | 东财 clist / push2delay |
| `high` | 0.5s | 东财 push2his（当前不可用，保留分级以便恢复后用） |

**为什么需要配速**：东财的间歇失败很可能就是限流。慢一点反而更稳——「硬怼会被封源」是 tdx-backtest 踩过的坑。

### 2.3 状态机与熔断

每个 `(资产, 源)` 维护运行态：

```js
// 状态：ok | degraded | down | unknown
// down    = 累计失败 >= 3 且最近 5 次全失败
// degraded= 有失败但也有成功
// ok      = 只有成功
// unknown = 还没调用过
```

熔断规则（内化自 HANDOVER §4）：

```
某源状态为 down → 写入熔断记录（until = now + cooldown）
在冷却期内：即使探活成功也**保持熔断**
冷却期结束：允许 다시 尝试，成功则解除
```

**冷却期默认 20 分钟**。理由：防止抖动——刚恢复就打过去、又被限流，会陷入"失败-恢复-失败"的循环。

**熔断状态必须落盘**（cron 与 Web 是两个进程，内存态不共享）：存 `ql.duckdb` 的 `meta` 表。

### 2.4 只记录，不造假

内化它最正确的一句话：

> **本层只做"记录与呈现"，不改变既有降级语义 —— 真实源失败仍直接抛错由上层兜底，绝不静默造假。**

意味着：健康层不负责"帮你想办法"，只负责"如实报告谁坏了"。兜底逻辑在各业务模块里显式写，不许藏在健康层。

### 3.3 板块 K 线（本地聚合，核心设计）

**上游没有任何源提供，全部自己算。**

```
输入：① 当日板块成分（来自 §3.2）
     ② 成分股的日线（来自上游 market.db 的 kline_daily，本地已有 1756 万行）
输出：板块日线序列 [date, open, close, high, low, volume, amount]
```

**算法（等权指数）**：

```js
// 对某板块，取所有成分股的日线，按日期对齐
// 每日涨跌幅 = 当日有数据的成分股涨跌幅的算术平均
// 指数序列 = 首日 1000，逐日累乘 (1 + 日涨跌幅)

function aggregateSector(membersKlines, { base = 1000, minMembers = 5, maxDailyChg = 0.31 }) {
  // 1. 建日期并集（升序）
  // 2. 每个日期，对每只成分股算 chg = close[i]/close[i-1] - 1
  //    · 跳过停牌（当日无 K 线）的股，不计入分母
  //    · |chg| > maxDailyChg → 非交易性变动，剔除该样本（见 §3.3.1 陷阱 2）
  //    · 有效成分数 < minMembers 的日期 → 该日板块不评分（标记 insufficient）
  // 3. 日涨跌幅 = mean(有效 chg)
  // 4. 累乘成指数序列
  // 5. open/high/low 同样按成分股均值合成（可选，用于画图）
}
```

**设计选择：等权而非市值加权。**

| 方案 | 优点 | 缺点 | 决定 |
|---|---|---|---|
| 等权 | 简单、抗大市值股绑架、更贴近"板块整体赚钱效应" | 小盘股噪音大 | **采用** |
| 市值加权 | 更接近真实指数 | 会被一两只巨无霸主导（如银行板块被工行绑架） | 提供但非默认 |

#### 3.3.1 两个必须防住的数据陷阱（2026-11-16 实战踩过）

**陷阱 1 · 跨市场同号：只按 `code` 取数会把两条序列串成一条**

上游 `kline_daily` 的主键是 `(market, code, date)`，**同一个 6 位代码可以同时存在于两个市场**：

| 代码 | sh | sz |
|---|---|---|
| 000001 | 上证指数（≈3700 点） | 平安银行（≈11 元） |
| 000016 | 上证 50 | 深康佳 A |
| 000688 | 科创 50 | 国城矿业 |
| 000852 | 中证 1000 | 石化机械 |
| 000905 | 中证 500 | 厦门港务 |

全库共 5 个这样的 code。旧实现 SQL 里 `SELECT market` 了却没用它过滤，两条序列按日期
交错塞进同一个数组，`aggregateSector` 的 `prevClose` 被来回覆盖 —— 单日涨跌幅算出
**+32393% / -99.70%**，金融行业板块 `ret20` 变成 **28502%**（221 个板块里 17 个超过 ±1000%）。

> **规则**：`readMemberKlines` 必须按 `(market, code)` 联合键取序列，一条序列一份，
> 绝不合并。调用方可传 `sh600000` 显式指定市场；传裸 6 位代码时按号段补
> （`92xxxx`→bj、`6/9`→sh、`4/8`→bj、其余→sz），与 `sina-sector.withMarket` 同一口径。
> 出现跨市场同号必须 `log.warn('localdb.code_market_collision')` 留痕。

**陷阱 2 · 单只成分股的非交易性跳变会绑架整条等权指数**

除权未复权、复牌首日、脏数据都会产生单日 ±50%~±30000% 的"涨跌幅"。等权平均里
一只票就能把整条指数带飞，而且这种错误**看不出来**——指数曲线还是平滑的，只是点位飞了。

> **规则**：单只成分股单日 `|涨跌幅| > maxDailyChg(0.31)` 的样本剔除，不算进当日均值
> 也不计入分母；但**价格照常推进**，否则下一日会连坐。阈值 31% 的依据：A 股单日理论
> 极限是主板 ±10%、双创 ±20%、北交 ±30%，31% 以上不可能是正常涨跌。
> 剔除数量记在 `meta[i].droppedCount`，可追溯。
>
> 注意跳变的**两个端点都要剔**：12 元→3600 元那天剔了，第二天 3600→12.13 的 -99.67%
> 同样要剔，只剔一端指数照样被打穿。

**必须明确的诚实边界**：

> **成分股用的是「当日成分」，不是「历史成分」。**

所以回算出来的历史板块序列有**幸存者偏差**——今天在板块里的股票，过去可能不在；今天被剔除的，过去可能在。

**因此**：
- ✅ 可用于**当日横截面比较**（今天哪个板块强）——这是主要用途
- ✅ 可用于**近 20~60 日的短期动量**（成分变动不剧烈，偏差可接受）
- ❌ **不可用于长期历史回溯或策略回测**（偏差会累积到失真）

这一条必须在 UI 上标注（板块详情页脚注：「历史强度基于当前成分回算，长周期仅供参考」）。

### 3.3.2 通达信网关（2026-11-18 接入，云端方案的关键）

**为什么接**：前面所有章节都指向同一个死结——**板块 K 线只能靠本地 38.5GB 上游库聚合**。
新浪没有板块指数，东财挂了，所以「换个没有 tdx-backtest 本地库的机器（比如云端）跑」
这件事从架构上就是不可能的。

通达信协议解开了这个结：它有**板块指数**（880xxx），板块指数本身就是一条日线序列。

```
本项目板块（新浪体系 new_jrhy / gn_hwqc）
        ↓ 名称映射（tools/tdx-map.js，只收高置信匹配）
通达信板块指数 880301 / 880471 ...
        ↓ tdx-gateway（Go，:7710）→ TCP 7709
一条真实的板块日线（含 upCount / downCount）
```

实测（2026-11-18）：

| 能力 | 结果 |
|---|---|
| 个股 / 指数 / 板块指数日线 | 250 根，**36–78ms** |
| 板块指数日线覆盖 | 12/12 抽查全部可用 |
| 板块成分（概念/地域/指数） | **269 / 161 / 117 个，一次请求 16.6 秒** |
| 名称→指数代码映射 | **604 条** |
| 个股统计（PE/股息/区间涨幅） | **8121 只，3.1 秒** |
| 行业归属（通达信 T + 申万 X） | 5669 条，0.44 秒 |
| 实时五档报价 | 37ms |
| **全市场快照** | **5583 只一次拿全，8.1 秒（命中代码缓存 3.2 秒）** |
| 单次报价上限 | **80 只**（协议限制，超了报「预期500个，实际80个」） |

**架构**：Go 库 + Node 项目之间隔一层 HTTP 网关，不是每次 spawn 子进程。
414 个板块指数串行拉一遍只要 20 秒；每个请求都重连 TCP 的话光握手就要几分钟。

```
Node (Express) ──HTTP──> tdx-gateway (Go, :7710) ──TCP 7709──> 通达信行情服务器
```

网关不是并发安全的（通达信协议本身不是），所以内部单连接 + 互斥锁串行。
代价是吞吐受限于单连接，收益是不会出现协议错帧。

**映射率只有 45%，这是刻意的。**

我们的 221 个板块（新浪）和通达信的 414 个（145 行业 + 269 概念）**不是一一对应**：
新浪叫「船舶制造」，通达信叫「船舶」；新浪的「金融行业」在通达信被拆成银行/证券/保险。
两种高置信规则（精确同名、去通用后缀同名）命中 99/221。

**明确不做模糊匹配**。实测用「最长公共子串 + 成分重合度」打分时出现过：

| 我们的板块 | 被误配到 | 相似度 |
|---|---|---|
| 锂电池 | **钠电池** | 0.53 |
| 固废处理 | **医废处理** | 0.59 |
| 新能源 | **新能源车** | 0.57 |

两个完全不同的板块被并成一个，比没配上危险得多——它会**静默给出错误的主线**，
而错误的主线会一路传导到预判卡和对账。所以剩下的 122 个板块宁可不配。

**降级路径**：有映射 → 板块指数；无映射 → 成分股等权聚合（需本地库）；本地库也没有 → 该板块标 `no_klines`（诚实缺失，不编）。

**无本地库时的实测**（模拟云端）：99 个板块成功算出强度、122 个标 `no_klines`、15.5 秒完成。
也就是说云端能把板块强度跑到 45% 的覆盖，剩下的一半是明确缺失而不是假数据。

**已知问题**：

1. **板块体系没有迁移**：要 100% 覆盖得把板块字典整体换成通达信的 414 个（code 变 880xxx），
   代价是历史 20 天 `sector_strength` 不可比（G8 必须记录口径变更）。
2. **资金流无解**：`GetTdxStat2` 解析的是 `tdxstat2.cfg`，里面只有成交额与板块归属
   （`BlockIndex`），**没有主力净流入**。东财 f62 挂了之后这一项没有替代源，
   评分走「成交额 + 量能」的降级口径（`net_inflow_missing`）。这是真实缺口，不是没接。
3. ~~`sector_strength` 降级运行时残留旧行~~ —— **已修**：`dao.del()` 落盘前先清当天，
   让「缺就是缺」而不是混着上一轮的值。本轮算出 0 个板块时不清（整体失败保留旧数据更安全）。
4. **板块成分仍走新浪**（221 次请求）。tdx 的 `GetTdxStat2.BlockIndex` 能反查
   「每只股票属于哪个板块指数」（5540 只有归属 / 520 个板块），但那属于 tdx 的
   板块体系，与现有 221 个新浪板块对不上，得跟第 1 条一起做。

**快照也走网关**（2026-11-18 补）

`market-snapshot` 原先只有新浪一条路。现在网关提供 `/snapshot`：一次返回全部
A 股 5583 只，字段含当日开高低收、成交量、**成交额**（成交额藏在内嵌 K 线里，
实测与新浪逐只对账 5/5 精确一致）。

两处坑，都已修：

| 坑 | 现象 | 原因 |
|---|---|---|
| 批量上限 | `预期500个，实际80个` | 通达信协议单次报价最多 80 只，必须 80 一批（5583 只 = 70 批） |
| 市场前缀丢失 | 输出全是 6 位码 | `Instrument.Code` 不含前缀，市场在 `Instrument.Exchange` 里；必须拼回 `sh600000`，否则 000001 沪深两只票会混淆 |

**历史日快照**（`/snapshot?date=YYYY-MM-DD`）

当日快照靠批量报价（8 秒），但报价永远只给「此刻」。要还原一个已经过去的交易日，
唯一数据源是 K 线——而通达信的 K 线接口是**按只查询**的，没有批量。

所以历史快照走逐只 K 线。**实测 0.25 秒/只**（比单只 70ms 慢，协议往返有额外开销），
5583 只 ≈ **20~23 分钟**。慢，但这是**云端回补的唯一路径**
（云端没有 market.db，`--from-local` 用不了）。

必须分片：一次拿完整份要 20 分钟，而 Node 的 `fetch` 默认 `bodyTimeout` 是
**300 秒** —— 分片前实测在 305 秒报 `fetch failed`，而网关那边还在白算
（进度跑到 4500 时客户端已断开）。现在按 500 只一片（约 130 秒）循环。

两条硬约束：
- 必须要求「K 线日期 == 目标日」。停牌的票没有当天 K 线就跳过，
  **绝不能拿更早的价冒充当日**（D3）
- 返回必须带上 `asOf = 目标日`，否则调用方会拿今天的时点去标它

用法：`node tools/daily-close.js --date 2026-11-20 --from-tdx`

**代价：没有换手率与流通市值。** 通达信报价协议里就没有这两个字段。
落 `null` 并标 `degraded: turnover_float_cap_missing`（D1：缺就是缺，不拿
volume/price 去估算）。影响面：选股器的换手率列会空，其余功能不受影响
（环境判定、对账、板块强度都不读这两个字段）。

**部署**：

```bash
npm run tdx:build     # 编译网关（Go ≥1.21）
npm run tdx:start     # 前台起 :7710，生产建议交给 launchd/supervisor
npm run tdx:probe     # 自检：网关可用性 + 板块指数 + 报价
npm run tdx:map       # 生成板块映射表（data/sectors/tdx-map.json）
```

网关二进制不入库（`tdx-gateway/bin/` 在 .gitignore 里），云端按平台重新 `go build`。

## 4. 实现要求

### 4.1 文件结构

```
lib/sources/
├── registry.js      资产注册表（唯一事实源）
├── health.js        运行态记录 + 状态机 + 熔断（落盘到 meta 表）
├── pacing.js        按风险等级节流
└── adapters/
    ├── sina-sector.js    新浪板块列表 + 成分
    ├── em.js             东财 clist / push2delay / push2ex
    ├── local-db.js       上游 market.db 读
    └── aggregate.js      板块 K 线聚合（纯函数）
```

**`aggregate.js` 必须是纯函数**（输入成分 K 线、输出序列），可离线单测，不碰网络。

### 4.2 每次调用必须做的三件事

```js
async function fetchAsset(assetKey, params) {
  const meta = ASSETS[assetKey];

  // 1. 熔断检查：主源在冷却期内 → 直接跳过
  for (const src of meta.sources) {
    if (health.isTripped(assetKey, src)) continue;

    // 2. 配速：等够最小间隔
    await pacing.wait(assetKey, src);

    try {
      const t0 = Date.now();
      const data = await ADAPTERS[src](params);
      health.record(assetKey, src, true, Date.now() - t0);   // 3. 留痕
      return { data, source: src, level: LEVEL[src], asOf: ... };
    } catch (e) {
      health.record(assetKey, src, false, null, e.message);
      // 继续试下一个源；全失败才抛错
    }
  }
  throw new NoSourceError(assetKey);   // 不许返回假数据
}
```

### 4.3 探活

**每 5 分钟一次**（内化 tdx-backtest 的 `source_health.py`），只在 Web 服务里跑：

```
对 ASSETS 里所有非 none 风险的主源，发一个最小请求
写 health 状态 + 熔断时间
结果进 /api/health 的 sources 字段
```

**不做成独立 cron**：Web 服务常驻，用 `setInterval(5min)` 即可；独立进程反而增加复杂度。

### 4.4 健康透出

`GET /api/health` 增加：

```jsonc
{
  "sources": {
    "sector-list-industry": {
      "state": "ok",
      "active": "sina-hy",
      "tripped": [],
      "sources": [

```

**要求**：`tripped` 非空时，前端必须显示"当前降级使用 X 源"。

## 5. 与 `04` 四因子的衔接（重要调整）

原 `04` 假设有上游板块 K 线。实测不可得，四因子的取数方式需按下表调整：

| 因子 | 原计划数据 | 实际数据 | 影响 |
|---|---|---|---|
| 动量 35% | 板块 K 线算 ret5/ret20 | **本地聚合序列**算 ret5/ret20 | 无影响，算法不变 |
| 资金 25% | 东财净流入 f62 | **默认走降级口径**（成交额分位 70 + 量比 30）；东财可用时才用 f62 | 精度下降，必须标 `degraded` |
| 宽度 20% | 板块涨跌家数 | **成分股快照实时算**（我们已有全市场快照） | 无影响，比上游更实时 |
| 持续性 20% | 板块 K 线算 MA20 之上天数 | **本地聚合序列**算 | 无影响 |

**结论**：四因子全部可算，只有「资金」默认降级。

**因此 `04` §2.1 的"数据源可用性验证"一节可以删掉**——已经验证完了，结论在本文。

## 6. 验收

| # | 断言 | 做法 |
|---|---|---|
| 1 | 板块列表能取到 ≥40 行业 + ≥150 概念 | 跑一次采集，断言数量 |
| 2 | 板块代码全部为新浪体系（`new_*`/`gn_*`） | 正则断言，出现 `BK` 开头即失败 |
| 3 | 成分股采集覆盖 ≥200 个板块 | 断言板块数 |
| 4 | 聚合出的板块日线，长度与成分股日线一致 | 抽查 5 个板块 |
| 5 | 有效成分 < 5 的日期被标记 `insufficient` | 构造小板块用例 |
| 6 | 东财全不可用时，四因子仍能全部算出 | 禁掉 em 源跑一次，断言无异常、资金因子 `degraded=true` |
| 7 | 熔断生效：连续 3 次失败后主源被跳过 | mock 适配器抛错，断言第 4 次不再调用主源 |
| 8 | 冷却期内即使探活成功也不恢复 | 构造 `down` + 探活成功，断言仍在 `tripped` |
| 9 | 全源失败时抛错而非返回空数据 | mock 全失败，断言抛 `NoSourceError` |

## 7. 已知限制（写进文档，避免以后当 bug 修）

| # | 限制 | 原因 | 何时能解 |
|---|---|---|---|
| L1 | 板块历史有幸存者偏差 | 只有当前成分，无历史成分 | 除非有历史成分数据源，否则不解 |
| L2 | 行业只有 49 个（比东财 496 粗） | 新浪一级分类 | 东财稳定时可增强，但不作为主键 |
| L3 | 资金因子默认降级 | 新浪无净流入，东财间歇 | 东财稳定后自动用上 |
| L4 | 概念板块 172 个（东财 554） | 新浪覆盖少 | 同上 |
| L5 | 板块 K 线是自己算的，与任何行情软件都不一致 | 等权、当前成分 | **这是设计选择，不是缺陷**；只要横截面排序正确即可 |

**L5 尤其重要**：不要试图去"对齐"通达信的板块指数，那需要历史成分与官方权重，成本远大于收益。我们要的是**排序正确**，不是**数值相同**。

**上游给什么就用什么，上游不给就自己算，上游时好时坏就当它坏。**
